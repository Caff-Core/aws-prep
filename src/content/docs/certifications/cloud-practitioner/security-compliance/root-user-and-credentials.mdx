## The idea in plain language

Every building has a master key that opens every door. Nobody carries it around on a normal day. It
sits in a safe, and its use is recorded.

The **root user** is the master key of an AWS account. It is the identity created with the account, and
it has full access to everything. Because it cannot be restricted the way other identities can, losing
control of it is very serious.

## Protecting the root user

AWS recommends the following:

- **Do not use it for everyday tasks.** Use other identities for daily work.
- **Use a strong, unique password**, and never share root credentials.
- **Register multi-factor authentication (MFA).** MFA is required for the root user in all account
  types.
- **Do not create root access keys.**
- **Use a group email address** for the account, so that recovery does not depend on one person.
- **Monitor root sign-in and use**, so that any activity raises an alert.

<ImportantConcept>
  Protect the root user by keeping it out of daily use. Put MFA on it, avoid access keys, and watch
  for any sign-in.
</ImportantConcept>

## Tasks only the root user can perform

A small number of tasks require root user credentials. The exam may ask you to recognise them.

- Changing a standalone account's email address, root password, or root access keys.
- Closing a standalone AWS account.
- Restoring IAM permissions if the only IAM administrator is locked out.
- Activating IAM access to the Billing console.
- Registering as a seller in the Reserved Instance Marketplace.
- Enabling MFA Delete on an Amazon S3 bucket.

Creating users or launching servers is not on this list. Those are everyday tasks for other identities.

## Everyday credentials

### Multi-factor authentication

**MFA** adds a second check beyond a password. AWS supports passkeys and security keys, which it
recommends because they resist phishing, along with authenticator apps and hardware tokens. AWS has
ended support for MFA by SMS.

### Access keys

**Access keys** are long-term credentials for command-line and programmatic access. Each has an access
key ID and a secret access key, and the secret can be retrieved only when the key is created.

Never store access keys in application code or project files. AWS prefers temporary credentials
whenever possible.

### Password policies

An **account password policy** sets rules for IAM user passwords, such as minimum length, required
character types, expiry, and preventing reuse. It does not apply to the root user's password.

## Storing secrets

Applications need passwords and keys, but these must not sit in code.

**AWS Secrets Manager** stores database credentials, API keys, and other secrets, and it can rotate them
automatically. **Parameter Store**, part of AWS Systems Manager, stores configuration values, including
encrypted ones. AWS recommends Secrets Manager for credentials.

<CostWarning>
  AWS Secrets Manager charges per secret and per API call. Parameter Store has a standard tier and
  an advanced tier, and the advanced tier has charges.
</CostWarning>

<RealWorldExample title="Real-world example: a leaked key">
  A developer in Gqeberha commits a long-term access key to a public code repository. Attackers find
  it within hours. If the application had fetched its database password from AWS Secrets Manager and
  used a role for AWS access, there would have been no long-term key to leak.
</RealWorldExample>

## What the exam expects

<ExamTip>
  **Closing an account** or **changing the root email** points to the root user. **Rotate database
  credentials automatically** points to AWS Secrets Manager. **First thing to do with a new
  account** usually involves protecting the root user with MFA.
</ExamTip>

## Common misconceptions

- **"Administrators should use the root user."** Administrators should use other identities.
- **"A password policy covers the root user."** It does not.
- **"SMS is a good MFA option on AWS."** AWS has ended support for it.

## Try it yourself (optional)

You need no AWS account for this, and it costs nothing. Enable multi-factor authentication on one
personal account you use, such as your email. It is the same habit AWS asks of its root users.

## Summary

<LessonSummary>

- The root user has full access, so keep it out of everyday use.
- Protect it with MFA, a strong password, and no access keys.
- A few tasks, such as closing a standalone account, require the root user.
- Access keys are long-term credentials that must stay out of code.
- AWS Secrets Manager stores and rotates secrets.

</LessonSummary>
